# 项目分期业务规格：工作流驱动的信息研究助理

**规格目录**：`specs/001-workflow-research-assistant`

**创建日期**：2026-10-19

**状态**：业务规格草案，需求质量检查通过，待用户审阅

**输入**：用户提出需求，由模型匹配已有工作流，用户选择后严格执行；从不同方向查询信息，按用户需要的内容格式及喜好整理并交付文档；候选均不适合时进入用户与助理协同探索模式，用户可见查询方向并控制执行方向，最终将执行过程整理成工作流；每次修改保存版本，默认展示最新版本。

**范围**：这是从零建设的项目完整业务规格，按最新要求分为两期。一期由用户先从列表选择固定工作流，再填写所需信息，聚焦稳定执行、文档输出和可直接使用的 UI；二期增加先描述需求、由模型匹配推荐后选择流程的入口，以及协同探索、探索结果沉淀和个人偏好管理。优先级表示所在期内的业务重要性，与期次分别标记。分阶段开发任务由后续 `speckit-tasks` 生成，本规格不进行技术选型。

**基线关系**：本次分期要求替代此前“全部故事均在首期”的约定。探索、探索沉淀和个人偏好管理明确移至二期，其需求保留。既有《需求.md》《PRD-一期.md》仅为历史参考，不据此自动恢复“仅旅游”等其他限制；旧技术方案不构成选型前提。项目宪章继续适用，此处仅表达可观察的业务约束。

**使用模式**：整个项目为单用户模式，所有工作流、任务、资料和文档由同一用户使用。两期均不要求多用户账号体系、租户、角色权限或用户间数据隔离；外部资料访问授权、凭据保护及必要的数据生命周期规则仍适用。

### 交付期次

| 期次 | 必须交付的业务范围 | 验收边界 |
|---|---|---|
| 一期 | 手动浏览并选择固定流程、按所选流程填写信息、严格执行、多方向查询整理、文档输出、版本记录、状态与异常处理、完整可用 UI | 用户通过 UI 完成“选流程—填信息—确认执行—获取文档”；不要求先描述需求，不进行模型匹配推荐或探索 |
| 二期 | 先描述需求再由模型匹配推荐并选择流程、协同探索与方向控制、探索过程沉淀、长期个人偏好管理及相应 UI | 保留一期直接选流入口，复用执行、文档与版本能力，跑通推荐及探索复用闭环 |

一期仍接受本次任务的喜好和输出要求，但不保存或自动读取跨任务个人偏好。后续规划和任务生成默认以一期为当前交付目标；二期不得成为一期发布前置条件。

## 澄清记录

### 会话 2026-10-19

- 问：一期选定工作流后，用户通过什么方式提出本次要求？ → 答：以聊天方式提出要求；助理收到输入后分析信息，发现缺失就向用户追问，最后将整理好的信息以列表展示，并使用一级、二级、三级标题组织内容。
- 问：看到整理后的要求列表时，用户如何修改其中的内容？ → 答：通过聊天提出修改，助理更新并重新展示完整列表，用户明确确认后才执行；一期不提供直接编辑列表条目的交互。
- 问：必要信息被追问后，用户回答“不知道”或“你帮我决定”时如何处理？ → 答：助理提供有依据的建议或可选项，必须得到用户确认后才能作为执行要求；最终完整列表仍须用户确认后才执行，无法确定的必要信息继续阻止执行。
- 问：用户没有主动说出本次喜好时，助理如何引导？ → 答：根据用户本次需要了解和探索的方向进行引导性询问，帮助用户确定需要的方向及相关喜好，不按所选工作流的预设偏好问题逐项询问；已有答案不重复询问，允许用户明确没有特别偏好。
- 问：用户表达多个难以兼顾的喜好时，助理如何引导取舍？ → 答：结合用户本次需要，用具体取舍问题引导，整理出优先顺序供用户确认，确认后才用于执行。
- 问：一期任务意外中断后如何继续，并如何处理写入或修改中的中断？ → 答：由用户点击“继续执行”，核验原输入、流程版本和已保存成果后，从最后可信的已完成步骤之后继续，未完整完成的步骤重新执行；涉及写入或对外修改时，必须先核对上次修改记录及实际结果，避免重复修改，结果不明时不得直接重做。无法安全恢复时说明原因，并仅在不会重复修改的前提下允许从头重跑。
- 问：继续执行、断点恢复及从更早节点重新运行时，执行记录如何关联？ → 答：采用类似 Git 分支的执行历史。继续执行和断点恢复沿用原执行 ID；用户可以选择工作流任意节点作为重新运行起点，从当前执行节点之前重新运行时，在当前执行记录上创建新分支，保留此前执行情况，各分支关联共同父执行记录，不覆盖原分支历史。
- 问：从节点创建执行分支时，是否允许修改本次要求？ → 答：允许通过聊天修改，重新展示完整要求列表并由用户确认；若修改影响所选起点之前的步骤，说明影响并提示用户将起点前移至受影响的最早节点，不能复用已不适用的成果。
- 问：主动停止及达到执行上限后如何继续？ → 答：区分暂停与取消；暂停后沿用原执行 ID 继续，取消后原执行结束，可创建分支重跑。达到上限必须停止新增行动并向用户求助，由用户判断当前执行中的问题及处置方式；只有用户明确批准追加额度和继续后才沿用原 ID 运行，累计消耗保留，不自动续跑。该求助规则当前为强制要求，后续根据实际使用情况另行调整策略。
- 问：一期是否允许多个执行分支同时运行？ → 答：不允许；整个应用同时最多运行一个执行分支，并且 LLM 只能单线程调用，即所有模型请求串行、最多一个请求在途。启动另一执行前必须先暂停或结束当前执行，核验在途写入结果并等待已有模型请求结束或确认取消。

## 用户场景与验收

### 用户故事 1 — 表达并确认研究需求（一期，优先级：P1）

作为用户，我希望在选择固定工作流后，通过聊天描述目标、范围、硬约束、喜好及文档要求。助理分析我的输入，追问缺失信息，并将整理好的要求用带一级、二级、三级标题的分层列表展示。二期需求优先入口可复用本故事的摘要和确认规则。

**优先级理由**：两种模式共同的输入基础。

**独立验收**：给定已选流程，用完整、缺失和冲突的输入检查确认摘要，无需实际查询。

**依赖**：一期依赖故事 11 的流程选择；二期模型匹配前的初始需求描述不依赖故事 11，选流后再按流程补齐输入。

**验收场景**：

1. **给定**已选择的工作流，**当**进入信息收集步骤，**则**通过聊天让用户描述本次想了解的事情，结合其描述引导明确需要的方向、目标、范围、硬约束、喜好及输出要求，再检查所选流程必要输入是否完整及范围是否适用；区分明确输入、默认值与待确认推断，不要求用户先逐字段填写表单，一期不读取长期偏好。
2. **给定**用户已经提交描述或补充回答，**当**助理分析信息并发现缺失，**则**针对缺失项向用户追问，收到回答后重新分析；已有明确答案不重复询问，必要信息未补齐前不能启动依赖该信息的执行，非关键项采用默认值时须明确展示。
3. **给定**冲突的硬约束，**当**确认需求，**则**要求用户解决冲突，不自行放宽；软偏好不能覆盖硬约束。
4. **给定**用户看到要求列表后通过聊天提出修改，**当**助理处理修改，**则**按当前所选流程更新要求并重新检查缺失与冲突，重新展示完整分层列表供确认，不自动重新选流；超出流程范围时说明原因，允许返回列表重新选择。
5. **给定**本轮要求已整理，**当**展示供用户核对的信息，**则**使用一级、二级、三级标题和标题下的列表项表达层级，例如一级“本次研究要求”、二级“范围与约束”、三级“必须满足的条件”，条目具体列出已收集内容；不得只输出一段连续文字或仅用缩进列表替代标题层级，不为凑层级编造用户要求。
6. **给定**最新要求列表已展示且必要信息完整、无未解决冲突，**当**用户明确确认执行，**则**按该列表对应的要求及已确认流程版本启动；仅展示列表、用户沉默或提出修改均不视为确认。任何修改都会使先前确认失效，须重新展示并确认；一期列表用于阅读核对，修改仅通过聊天提出。
7. **给定**用户对追问回答“不知道”或“你帮我决定”，**当**助理提供建议或可选项，**则**说明建议依据并标为待确认，不将此类回答当作接受尚未提出的具体建议；用户明确接受后才补入执行要求。接受建议不等于启动执行，最终完整列表仍须用户明确确认执行；无法确定的必要信息继续保持缺失并阻止启动。
8. **给定**用户描述了想了解的事情但方向或喜好尚不明确，**当**助理继续对话，**则**根据本次描述及后续回答进行引导性询问，帮助用户明确想重点了解什么、为何关注、喜欢或不喜欢什么以及更看重什么，不按工作流预设的偏好题目逐项询问；已有答案不重复追问，明确“没有特别偏好”可作为有效回答，不擅自补出喜好。
9. **给定**引导中形成了需要的方向及喜好，**当**整理供确认的信息，**则**将其纳入完整分层列表，区分用户明确表达与助理提出的待确认建议；建议须经接受，完整列表须经确认才执行。该引导属于执行前需求澄清，不开展信息研究、不改变固定流程步骤；若确认的需要超出所选流程范围，说明不适用并允许返回重选，不自动进入二期探索模式。
10. **给定**用户表达多个难以兼顾且尚未明确优先顺序的喜好，**当**助理引导取舍，**则**结合本次方向提出具体比较问题，例如“价格稍高但交通更方便，是否可以接受”，根据回答整理优先顺序和用户明确的可接受条件，纳入完整分层要求列表供确认；示例须明确是假设情境，不冒充已查得的方案，不擅自生成数值权重或放宽硬约束。优先顺序未明确时保持待确认，不将其作为已确认规则执行。

### 用户故事 2 — 查看模型匹配结果并选择工作流（二期，优先级：P1）

作为用户，我希望先描述需求，再看到模型推荐的已有工作流及适配理由，自主选择一个执行或进入探索。这是二期新增入口，一期直接从列表选流无需模型匹配。

**优先级理由**：连接需求与可复用研究方法，保留用户选择权。

**独立验收**：使用已知适用范围的流程集合检查匹配、选择及无匹配分支。

**依赖**：故事 7 的可用版本，复用故事 1 的需求确认规则；先收集初始需求再匹配，选流后补齐流程输入，不把一期手动选流设为匹配前提。

**验收场景**：

1. **给定**存在相关流程，**当**模型匹配，**则**展示候选用途、适配理由、未覆盖内容、必要输入、主要步骤、预期产出及版本，不虚构已有流程。
2. **给定**候选列表，**当**用户未选择并确认，**则**不自动执行；选择后必须补齐所选流程要求的必要输入。
3. **给定**全部候选不适合或没有候选，**当**查看后续操作，**则**允许修改需求、直接查看已有流程或进入探索，不自动选择不适用流程；进入探索时带入已确认需求。
4. **给定**流程库为空或匹配失败，**当**展示结果，**则**明确区分原因，提供返回列表、重试或探索等适用操作，不能伪装为匹配成功。
5. **给定**候选展示后出现新版本，**当**用户准备执行，**则**提示变化并重新确认实际版本，不静默替换已选内容。

### 用户故事 3 — 严格按流程研究信息（一期，优先级：P1）

作为用户，我希望助理按选定流程，从规定的不同方向查询、核查和整理信息，知道执行进度及缺失部分。

**优先级理由**：兑现严格遵循工作流的核心承诺。

**独立验收**：提供固定版本、有效输入及已知材料，核查步骤、条件与信息方向。

**依赖**：一期依赖故事 11、1、7；二期可由故事 2 选流后进入，不依赖模型匹配即可执行。

**验收场景**：

1. **给定**已确认流程和输入，**当**执行，**则**固定本次版本与输入，遵守步骤顺序、条件分支、范围及完成条件，展示当前和已完成步骤。
2. **给定**至少两个查询方向，**当**收集信息，**则**每个方向都有结果或缺失说明；重要事实关联来源和获取时间，可获得时记录发布时间或更新时间。
3. **给定**来源失败或步骤不能完成，**当**继续处理，**则**只能采用流程允许的有界重试或替代路径；无允许路径时停止依赖该步骤的行动，不跳过必需步骤后宣称完成。
4. **给定**模型或外部资料建议改变步骤或约束，**当**处理建议，**则**保持已确认规则；一期用户希望改变结构时须先结束当前任务，更新流程形成新版本并重新确认执行，不原地篡改实例；二期可明确转探索并保留关联。
5. **给定**重复、矛盾、过期或未证实材料，**当**整理，**则**去重、归类并标记已发现问题，区分事实、来源评价和助理推断，未知条件不视为合格。

### 用户故事 4 — 按本次要求获得文档（一期，优先级：P1）

作为用户，我希望得到符合约定内容结构、详略、语言及关注重点的文档，能够获取并核查来源。

**优先级理由**：两种模式共同的最终交付。

**独立验收**：用同一批材料与不同输出要求检查文档，无需重新执行研究。

**依赖**：一期依赖故事 1、3；二期复用于故事 5，不以探索为一期前置条件。本次任务喜好可生效，无需故事 8 的长期偏好管理。

**验收场景**：

1. **给定**报告、清单或对比表等内容要求，**当**生成文档，**则**符合约定结构，包含目标、约束、结果、取舍理由、来源及缺口；不支持的交付格式须在执行前说明并协商替代。
2. **给定**不同偏好，**当**整理相同材料，**则**排序、篇幅或说明体现相关偏好；违反硬约束的内容不得作为合格推荐，关键条件未知项明确标为待确认。
3. **给定**没有合格结果或仅部分完成，**当**交付，**则**说明实际情况及原因，不凑数、不编造、不隐瞒缺口。
4. **给定**已生成文档，**当**获取并再次打开，**则**内容完整可读且来源保留；交付失败时保留已有内容并允许重新获取，不误报已交付。

### 用户故事 5 — 协同探索并掌握查询方向（二期，优先级：P1）

作为用户，我希望在已有工作流不适合时，与助理共同探索，看到正在查什么、为何查及发现什么，并及时调整方向。

**优先级理由**：二期新增完整研究路径，需求保留，不参与一期发布验收。

**独立验收**：在空流程库中发起探索，确认并调整方向，结束后检查成果。

**依赖**：故事 1；故事 2 提供常规入口，文档交付复用故事 4。

**验收场景**：

1. **给定**进入探索，**当**开始查询前，**则**展示初始方向、目的、范围及预期产出，由用户确认或调整。
2. **给定**探索正在执行，**当**查看过程，**则**看到当前及计划下一方向、已执行动作和发现摘要，不只在结束后展示；不要求展示模型内部逐字推理。
3. **给定**用户增加、删除方向、调整优先级或缩小范围，**当**接收指示，**则**确认生效范围，下一项新增行动遵守最新指示；已开始且不能立即停止的动作须说明，其迟到结果不得覆盖新指示或自动成为已接受成果。
4. **给定**助理拟扩大目标、硬约束、授权或已确认范围，**当**提出调整，**则**先等待用户确认；未回应时不擅自扩展。
5. **给定**成果充足或用户要求结束，**当**结束研究，**则**按现有成果交付完整或部分文档，并保留过程供工作流提炼；取消时说明已保留成果。

### 用户故事 6 — 将探索沉淀为可复用工作流（二期，优先级：P1）

作为用户，我希望将有效探索过程整理成工作流，审阅后保存，以后类似需求能够直接复用。

**优先级理由**：完成需求、探索、沉淀、匹配与执行的闭环。

**独立验收**：提供完整探索记录，生成并确认草稿，用另一组有效输入验证复用。

**依赖**：故事 5、7；复用验收连接故事 2、3、4。

**验收场景**：

1. **给定**探索记录，**当**提炼流程，**则**生成包含用途、适用边界、可变输入、步骤、查询方向、判断与分支规则、输出、完成条件及执行上限的草稿，并关联原记录。
2. **给定**过程含试错、纠偏及任务专有信息，**当**整理草稿，**则**保留有效决策条件、说明未采纳路径，将专有值转换为待填输入，不把旧答案当作流程步骤。
3. **给定**可审阅草稿，**当**用户修改并确认保存，**则**形成首个可用版本并进入列表及匹配范围；未确认草稿不作为可执行流程推荐。
4. **给定**已保存流程，**当**采用另一组符合范围的输入执行，**则**生成对应新文档，不以旧答案冒充查询；失败时说明适用性问题并允许修改成新版本。
5. **给定**探索中断或草稿缺少必要定义，**当**保存，**则**可保留草稿但不能成为可执行版本；已完成的文档交付不依赖用户立即确认草稿。

### 用户故事 7 — 修改流程、保留版本并默认查看最新（一期，优先级：P1）

作为用户，我希望每次修改都留下版本，默认看到最新内容，也能查阅历史及任务实际使用的版本。

**优先级理由**：支持流程演进并保护执行一致性和可追溯性。

**独立验收**：对一个流程连续修改保存，同时保留旧版本运行实例，检查列表、历史及关联。

**依赖**：无上游执行依赖，可用预设流程验证；为故事 2、3、6 提供基础。

**验收场景**：

1. **给定**已有流程，**当**名称、描述、输入、步骤、规则、输出或边界的任一修改保存，**则**新增唯一版本，记录时间及变更摘要，不覆盖旧版本；不要求通过用户身份区分修改者。
2. **给定**多个保存版本，**当**打开默认列表或详情，**则**采用最新已确认可用版本；历史入口可查看完整旧定义与变更摘要，未确认草稿单列；二期模型匹配同样使用最新可用版本。
3. **给定**任务正在使用旧版本，**当**新版本保存，**则**运行及文档保持原版本关联；新任务默认最新版本并由用户确认。
4. **给定**基于过时版本编辑或保存失败，**当**提交，**则**提示冲突或失败，保留原有效版本及待保存修改，不静默覆盖较新内容，不把失败版本显示为最新。

### 用户故事 8 — 管理可复用个人偏好（二期，优先级：P2）

作为用户，我希望显式保存常用偏好并能查看、修改、清空和删除，减少重复填写。

**优先级理由**：二期改善重复使用体验；一期仅保留故事 1、4 中本次任务要求生效，不包含跨任务偏好保存、读取或管理。

**独立验收**：保存偏好后在新任务读取、覆盖、清空并删除，检查实际采用值。

**依赖**：故事 1；结果影响通过故事 4 验证。

**验收场景**：

1. **给定**本次偏好，**当**用户明确选择长期保存，**则**保存且可查看修改；未授权时不自动从历史行为推断长期偏好。
2. **给定**已保存偏好，**当**新建任务，**则**展示相关采用值；本次明确输入或清空优先，本次覆盖不自动改写长期偏好。
3. **给定**偏好已删除，**当**新建任务，**则**不再使用；历史执行保留原输入依据，不倒改历史结论。

### 用户故事 9 — 查看状态、停止执行及处理异常（一期，优先级：P1）

作为用户，我希望知道进展和停止原因，能够主动停止，失败或中断后仍可辨认已有成果及下一步选择。

**优先级理由**：两种模式都不能无限执行或虚报成功。

**独立验收**：给定运行记录，触发等待、超时、取消、中断及重新打开，检查状态与产物。

**依赖**：一期依赖故事 3、4；二期扩展至故事 5。

**验收场景**：

1. **给定**任务运行或等待用户，**当**查看或重新打开，**则**显示模式、步骤、已完成部分、等待原因及执行上限，不把等待误报为查询中。
2. **给定**用户点击暂停或取消，**当**系统处理请求，**则**停止新增行动并保留有效成果，明确显示请求处理中及最终状态；暂停不是终态，用户明确继续并通过必要核验后沿用原执行 ID，取消则结束原执行，不能直接恢复，只能经确认创建重跑分支。无法即时停止的动作不得在界面被宣称已停止，迟到结果不得自行解除暂停或取消；实际已生效的写入仍追加记录并核验，不能为了保持状态而隐瞒修改事实。
3. **给定**任务因应用崩溃、断电等意外中断，**当**再次查看，**则**显示最后可信状态及未完成步骤并提供“继续执行”；只有用户主动点击后才核验原确认输入、原流程版本、已保存成果的完整性和适用性，通过后从最后可信的已完成步骤之后继续，未完整完成的步骤重新执行，但写入或修改操作必须先遵守场景 5 的结果核验规则。应用恢复运行不自动续跑；无法安全恢复时说明原因，仅在已排除重复修改风险后允许从头重跑，不误报成功。
4. **给定**用户继续执行、断点恢复或仅重试文档获取，**当**操作完成，**则**沿用原执行 ID，追加恢复、重试及结果记录，不覆盖此前的中断、操作或成果记录；恢复后当前状态可以推进，但历史事实保留。若用户从当前执行节点之前重新运行（包括从首节点重跑），则按场景 6 创建执行分支，不将其伪装为同一次续跑。
5. **给定**中断发生在文档保存、其他写入或已获授权的修改期间，**当**用户请求继续或从头重跑，**则**先核对上次操作记录及目标的实际结果：已确认完成则复用结果，不重复修改；已确认未生效且允许重试才重新执行；部分生效、结果不明或目标随后被改动时，暂停受影响步骤及其依赖步骤，说明已知情况和待核验内容，等待明确处置，不通过从头重跑绕过核验。记录至少能辨认操作目标、拟进行的修改、发生时间、关联步骤及已确认结果；在可能修改目标前须留存可追溯操作记录，无法留存时不执行该修改。确认生效的操作与其记录均保留，恢复不覆盖原始事实。

6. **给定**已有工作流执行记录，**当**用户选择一个更早节点重新运行，**则**在当前执行历史上创建具有独立执行 ID 的新分支，记录共同父执行记录、分叉节点、创建原因及时间，使原分支与新分支可追溯至同一父执行历史；保留分叉前的执行情况及有效成果引用，新分支从所选节点开始重新执行，原分支的过程、状态和文档不被覆盖。用户可浏览节点并选择任意节点作为起点，但启动前须检查其前置条件和写入影响，不能借此跳过未满足的必需前置步骤。
7. **给定**新分支准备从所选节点开始，**当**检查可复用成果，**则**只复用该节点之前且经完整性、时效及适用性核验的前置成果；所选节点及其后续步骤原有结果只作为历史，不冒充新分支已完成结果。缺少有效前置成果时，明确说明阻塞节点并让用户选择可行的更早起点，不自行改变所选起点；涉及已发生的写入或修改时仍须核对父执行及相关分支的操作记录和实际目标结果，创建新 ID 不授权重复修改。

8. **给定**用户准备创建执行分支并通过聊天修改本次要求，**当**助理分析修改，**则**保留原分支的输入与确认记录，为新分支整理完整要求列表并重新请求确认，记录新旧要求差异及受影响节点。若影响早于所选起点，说明失效成果及最早受影响节点，用户确认前移起点后才能启动；用户不接受前移时保留待确认内容，不按原起点强行运行。无法确定影响范围时不假定旧成果仍有效，说明不确定性并请用户确认从可验证的更早起点重跑。新分支仅复用未受影响且核验有效的前置成果，原执行 ID 下的继续或恢复不得静默改变已确认输入。

9. **给定**执行达到时间或资源上限，**当**触发上限处理，**则**停止新增行动并进入“等待用户处理”，保留原执行 ID、累计消耗和有效成果，必须向用户发起求助；说明已完成与未完成步骤、触及的上限、当前阻塞或异常、已尝试的处理及可选处置，未知原因明确说明，不将推测当作确定诊断。用户决定问题如何处理；未回应时保持等待，不自动加额度、恢复、创建分支或换任务绕过上限。
10. **给定**任务因达到上限等待用户，**当**用户作出处置决定，**则**记录决定与时间：只有明确批准追加额度和继续、且通过写入结果等必要核验后，才以原 ID 恢复并保留累计消耗；用户选择调整要求时进入新分支确认流程，选择取消则结束原执行。仅回复“知道了”或讨论问题不算继续授权；仍未明确解决阻塞时继续等待。此求助规则为当前强制业务行为，后续基于实际使用反馈的策略变更必须明确更新规则，不能由执行中的助理自行改变。

11. **给定**应用中已有一个执行分支正在运行，**当**用户启动或恢复另一个任务或分支，**则**不同时运行，提示先暂停或结束当前执行；不自动取消旧执行或自动排队启动新执行。只有旧执行已停止新增行动、在途动作已收敛且写入结果已核验后，才允许用户明确启动另一执行；原执行保留其 ID、状态和历史。
12. **给定**应用需要调用 LLM，**当**已有一个模型请求在途，**则**不得发起第二个请求，所有任务、分支、需求澄清、建议生成、文档生成及重试均遵守应用级串行调用。请求超时但尚不能确认结束或取消时，不把超时提示当作空闲状态，不并发重试；暂停或取消也不能立即释放未确认结束的请求。UI 应说明正在等待，后续调用仅在前一请求结束或确认取消后进行，不因串行安排绕过用户确认及执行上限。

### 用户故事 10 — 通过完整 UI 独立完成任务（一期，优先级：P1）

作为单用户，我希望直接通过可用界面先选流程，再填信息、执行研究、查看进度和获取文档，不需要编写命令或操作内部数据。

**优先级理由**：用户可直接使用的 UI 是一期交付条件，不能用仅有执行能力或界面原型代替。

**独立验收**：在已具备可用固定流程的环境中，从打开界面开始完成一次真实研究，查看进度并获取文档，另外检查失败和空状态。

**依赖**：故事 11、1、3、4、7、9；不依赖故事 2、5、6、8。

**验收场景**：

1. **给定**应用已完成必要的初始配置，**当**用户打开 UI，**则**直接进入已有工作流列表，不要求先输入自然语言需求，也无需注册、用户切换、租户或角色配置。
2. **给定**可用工作流，**当**用户仅通过 UI 操作，**则**依次完成浏览详情、选择流程、聊天描述要求、回答缺失项追问、查看带一级至三级标题的要求列表、确认版本及输入、执行、查看状态、阅读并保存文档；不要求命令或手工处理内部数据。
3. **给定**缺失输入、所选流程不适用、空库、执行失败或交付失败，**当**查看对应界面，**则**显示原因及适用的补充、返回重选、重试或重新获取操作，不留下无反馈按钮或虚假成功提示。
4. **给定**任务执行中，**当**用户在界面暂停、取消或离开后重新打开，**则**能看到可信状态、原因及已有成果，暂停与取消操作分别得到明确反馈；达到上限后必须显示求助及等待处理状态，用户可查看问题并提交处置决定，不以仅显示“额度不足”代替求助。
5. **给定**查看或修改固定流程，**当**使用 UI 操作，**则**可查看定义、实际版本和版本历史，修改已有定义并保存新版本；保存失败显示原因并保留待保存内容，不要求一期具备通用可视化流程编排器。
6. **给定**一期发布版本，**当**使用主路径界面，**则**动作连接实际执行与真实文档，不以静态演示替代；不要求模型匹配推荐、配置长期偏好或进入探索才能继续。
7. **给定**已有执行历史，**当**用户查看执行详情，**则**可以查看工作流各节点、执行 ID、父执行关系、分叉位置和各分支的状态及产物，选择节点重新运行或对可恢复执行点击继续；界面明确区分“沿用原 ID 继续”与“从更早节点创建分支”，不要求使用 Git 或命令操作。

### 用户故事 11 — 先从列表选择固定工作流（一期，优先级：P1）

作为用户，我希望先浏览已有工作流的用途和产出，直接选中一个，再填写其需要的信息。

**优先级理由**：这是一期研究任务入口，与二期根据需求推荐候选的选择方式区分。

**独立验收**：提供两个已有流程，不输入研究需求即可浏览、选择并进入对应填写步骤。

**依赖**：故事 7 的可用流程版本，不依赖故事 1 的输入或故事 2 的模型匹配。

**验收场景**：

1. **给定**已有流程，**当**打开列表及详情，**则**能查看用途、适用范围、必要输入、主要步骤、预期产出及最新可用版本，无需先描述需求或等待模型推荐。
2. **给定**用户选中流程，**当**继续，**则**进入该流程的聊天信息收集步骤，选择本身不立即执行；经分析、必要追问、分层列表展示及用户确认后才可启动。
3. **给定**流程库为空或用户认为没有合适流程，**当**查看入口，**则**如实显示状态，允许返回或结束，不伪造可用流程，不自动匹配或探索。
4. **给定**已填写部分信息，**当**用户返回并改选流程，**则**展示新流程的输入要求，对保留的适用信息重新确认，不将旧流程专用字段直接用于新流程。
5. **给定**选流后版本发生变化，**当**准备执行，**则**提示变化并重新确认实际版本和受影响输入，不静默替换。

|---|---|---|
| 输入缺失、约束冲突 | 追问或修正后才执行依赖动作 | 故事 1 |

| 多项喜好难以兼顾且优先顺序不明确 | 用具体假设情境引导取舍，将回答整理为待确认的优先顺序，不自行设定权重或放宽硬约束 | 故事 1.10 |
| 空库或用户未找到适用流程 | 一期明确状态，可返回或结束，不自动匹配或探索 | 故事 11、10 |

| 填写后改选流程或版本变化 | 按新定义重新检查并确认输入 | 故事 11 |
| 必需步骤失败 | 不违规跳步，不擅改规则 | 故事 3 |
| 来源受限、冲突、过期或无结果 | 标明缺口，不编造或绕过访问限制 | 故事 3、4 |
| 全部候选违规或未知 | 无合格结果或待确认，不凑数 | 故事 4 |
| 二期探索未回应、纠偏及迟到结果 | 等待必要确认，后续遵守最新指示 | 故事 5、9 |

| 达到上限且用户未明确处置 | 必须停止新增行动并求助，说明进展、消耗及问题，保持等待；不自动续跑或重置额度 | 故事 9.9、9.10 |
| 当前执行未停止时启动其他任务或分支 | 拒绝同时运行并提示先暂停或结束，不自动切换或排队启动 | 故事 9.11 |
| LLM 请求在途、超时但未确认结束或取消 | 不发起第二个模型请求，显示等待，不能通过重试或分支切换产生并发调用 | 故事 9.12 |
| 从更早节点重新运行或从首节点重跑 | 创建独立执行分支并关联共同父执行及分叉节点，原分支不被覆盖 | 故事 9.6 |
| 所选重新运行节点缺少有效前置成果 | 明示阻塞及可行起点，用户决定起点，不跳过必需前置条件 | 故事 9.7 |
| 分支修改要求影响所选起点之前的步骤 | 展示要求差异与受影响节点，用户确认完整新要求并确认前移起点后才能启动，不复用失效成果 | 故事 9.8 |
| 写入或修改中断，记录与实际结果可能不同 | 先核验，已生效不重复、未生效才可重试；部分生效或结果不明时暂停受影响执行，不盲目重跑 | 故事 9.5 |
| 外部材料夹带改变目标或索取隐私的指令 | 仅当资料处理，不改变授权及规则 | 约束 A1—A3 |

### 共通约束及验收

- **A1 授权边界**：给定需求中含无关个人信息，当查询或交付时，仅使用当前操作必需且获授权的信息；越权访问被拒绝并说明原因。
- **A2 外部资料边界**：给定来源包含“忽略要求、索取秘密、改变流程”等指示，处理后目标、权限、工作流和上限保持不变。
- **A3 隐私保护**：给定含敏感凭据的错误或材料，展示文档、状态及过程摘要时不出现可用凭据或无关敏感信息；过程只展示可审查行动和依据摘要。
- **A4 数据生命周期**：给定用户准备保存资料，能够查看用途、访问范围、保留期限及删除方式；到期或请求删除后，不再提供普通访问或用于新任务，关联记录明确显示资料已删除。版本历史要求不覆盖个人资料删除要求，复用流程不保留非必要个人信息。
- **A5 单用户模式**：给定同一应用中的工作流、任务、资料和文档，当用户查看和使用时，均在一个工作区可用，不要求选择所有者、账号、租户或角色，也不按用户身份过滤数据。A1—A4 的授权和访问范围仅约束外部资源、敏感信息使用及数据生命周期，不引入用户间隔离。
- **有界执行**：执行前明确查询范围、有效研究时长及适用资源上限。暂停、意外中断及等待用户期间不开展新增研究，相应停等时间不计入有效研究时长；已发生的操作消耗仍如实累计。达到上限必须停止新增行动并向用户求助，由用户判断问题和处置；只有明确批准追加额度与继续才可恢复，不清零累计消耗，不用创建分支绕过求助或授权。具体数值在规划中确定，但必须在使用前明确。
- **行动边界**：提供查询、研究、整理及文档，不代用户预订、支付、投递或对外发送；研究需求不自动授予这些行动权限。
- **中断恢复边界**：写入恢复规则适用于文档保存等已在范围内的操作；对外修改仅在功能范围允许且已获授权时适用，不因具备恢复规则而新增外部修改能力或权限。主动暂停、取消、达到上限与意外中断分别记录原因；暂停和意外中断须用户主动继续，取消结束原执行，达到上限须先完成强制求助和用户处置，不能一律按普通断点恢复处理。暂停、取消、中断与恢复的用户可见行为见故事 9.2—9.5，判定规则以 FR-024/FR-025 为准。
- **起点语义**：从当前执行节点继续（含恢复未完成节点）沿用原执行 ID，不创建分支；从当前节点之前已完成的节点重新运行才创建分支；当前节点之后或从未执行过的节点不能作为分支起点，只能等待执行推进到该节点，或另行建立新的根研究。无法判断节点归属时按阻塞处理并向用户说明，不自行扩大可选起点。
- **串行执行约束**：同时最多一个执行分支运行；不同研究任务也不例外。LLM 单线程调用的业务含义为整个应用同时最多一个模型请求在途，不限定具体实现技术。需求澄清和文档生成等模型调用共享此限制；已有执行等待人工处理时可以查看记录，但不得在在途模型或写入尚未处理完毕时启动另一执行。后续阶段新增功能同样遵守该约束，除非用户明确修改规则。

### 关键业务实体

- **研究需求**：目标、范围、约束、本次喜好及优先顺序、用户明确的可接受取舍条件、输出要求、来源及确认状态，关联用户原始描述、补充回答、仍缺失的信息和供用户核对的分层要求列表；助理建议保留依据及待接受或已接受状态，与用户对最终完整列表的执行确认分别记录。
- **个人偏好（二期）**：明确保存的跨任务偏好、适用范围和更新时间，可被本次要求覆盖；一期任务输入中的喜好不构成长期偏好实体。
- **工作流**：可复用研究方法的稳定身份，关联用途、历史及最新可用版本。
- **工作流版本**：某次保存的完整定义，包含输入、步骤、规则、分支、输出、上限和完成条件及变更记录。
- **匹配结果（二期）**：需求与模型推荐候选版本的对应、理由、缺口和用户选择；一期手动选流不依赖此实体。
- **执行实例（执行记录）**：具有独立执行 ID，包含模式、确认输入、实际版本或探索过程、当前节点、状态、产物、上限、累计消耗及停等或终止原因；区分运行、暂停、意外中断、等待用户处理和取消等状态。继续及断点恢复沿用此 ID，过程记录仅追加。用户独立发起的研究建立新的根执行，从更早节点重跑则建立有关联的新分支。
- **执行求助与处置记录**：关联执行 ID、触发上限、当时的累计消耗、完成情况、问题与不确定性、已尝试措施、用户决定、批准的追加额度及继续授权；等待与恢复过程可追溯，不以记录求助本身视为问题已解决。
- **执行分支关系**：关联共同父执行记录、原分支与新分支、分叉节点、创建时间及原因，记录新旧要求差异、受影响节点、实际确认起点及新要求确认记录；各分支具有可区分的执行 ID，保留父执行历史及前置成果来源，不复制后将旧成果冒充新执行结果。分支表示同一研究历史中的不同执行路径，不等同于二期探索模式。
- **节点执行记录**：关联执行 ID、工作流节点、执行尝试、状态、输入依据、成果引用及异常；续跑或恢复追加尝试记录，保留此前尝试，分支可追溯复用成果来自哪个父执行节点。
- **写入或修改操作记录**：关联执行及步骤，记录目标、拟进行的修改、时间、已确认结果及核验情况；区分未生效、已生效、部分生效和结果不明，用于避免恢复或重跑时重复修改。记录写入意图不等于实际修改已成功，须结合实际结果核验。
- **查询方向与行动记录**：目的、范围、动作、结果摘要、时间、顺序及用户指示关联。
- **来源与证据**：名称、定位信息、获取及发布时刻、支持的事实、缺口和冲突。
- **用户指示（二期）**：探索调整的内容、确认时间、采纳情况及生效边界。
- **探索工作流草稿（二期）**：待确认流程、原探索关联、缺失项及修改记录；一期已有流程编辑中的待保存内容不依赖探索草稿能力。
- **交付文档**：关联执行和实际版本、约定结构、结果、理由、引用、缺口及交付状态。

### 计量口径

SC-005、SC-006、SC-012 的比率按下列口径计算，由 `docs/acceptance-matrix.md` 在 T098 逐例记录；口径变更必须同步修订本规格。

- **重要外部事实**：影响合格性判断、结论或推荐排序的事实。来源覆盖率 = 有来源或已标“未证实”的事实数 ÷ 报告中列出的重要外部事实总数，仅统计正文明确列为事实或依据的条目。
- **必需栏目**：执行前已确认的输出要求中约定的栏目。栏目覆盖率 = 实际包含且内容非空的栏目数 ÷ 约定栏目数。
- **缺口**：已识别的来源缺失、无合格结果、未证实、冲突及过期项。缺口披露率 = 文档中明确披露的缺口数 ÷ 已识别缺口总数。
- **完整与部分**：全部约定栏目非空、全部硬约束均有 SATISFIED/VIOLATED/UNKNOWN 结论、全部已识别缺口已披露，才计为完整（COMPLETE）；任一条件不满足时必须标部分（PARTIAL）或无可合格结果（NO_QUALIFIED_RESULT），不得计作完整成功。

## 假设与范围说明

1. 两期均采用单用户模式，全部数据供同一用户使用，不要求多用户账号、角色、租户或用户间隔离。用户与助理协同探索属于二期，组织审批和工作流市场不在当前范围。
2. 每次保存内容修改形成版本，不按每次按键形成版本。“最新”指最新已保存且确认可执行的版本，草稿单列。历史查看属于首期；历史回滚和直接启动旧版本不作为默认必需能力。
3. 首期需有少量已有流程支持真实选择，验收至少准备两个不同适用范围的流程；主题在规划中确定。旅游是可选案例，不限定项目只能处理旅游。
4. 文档格式包含结构及获取形式；至少支持报告、清单、对比表内容组织，以及一种可保存的文档交付形式。不假设任意专有文件格式均支持，不支持须执行前协商。
5. 二期探索初始方向须确认，已确认范围内的具体查询不逐次审批，但用户可介入。扩大范围、改变目标、硬约束或权限必须再次确认。
6. 一期固定模式只在流程允许的参数与分支内执行，不能自行改变结构；需要修改时结束旧任务、保存新版本后重新发起。二期显式转探索保留原记录和关联。
7. 不保证所有来源可访问或信息均为实时；来源质量、可访问性及用户必要反馈是外部业务依赖，缺失时按边界场景处理，不能因此删除核心能力。
8. 长期个人偏好保存、读取及管理在二期；一期只处理本次任务要求。两期均不默认要求自动学习长期偏好、历史全文检索、定时执行或无人值守自动续跑；不影响必要的版本历史、过程记录和中断识别。
9. 数据保留期限和具体资源上限在规划阶段明确为政策并在使用前展示；规则本身属于首期强制要求，不预设技术实现。
10. 一期 UI 必须实际可用，覆盖故事 10 的完整业务链和异常反馈。具体页面布局和技术实现留待规划，不允许把 UI 延至二期或以静态原型代替一期交付。
11. 一期手动列表选择仍是必需能力；移至二期的是“先输入需求—模型匹配推荐—从候选中选择”的入口，不是取消一期选流。两种入口不得混淆，一期不以模型推荐成功作为填写或执行的条件。
12. 本规格中的“填写信息”或“填信息”均指选流后的聊天描述、补充回答和要求确认，不指强制字段表单。此处一级、二级、三级标题的格式要求针对执行前的要求整理展示；最终研究文档仍按本次约定的输出要求生成。
13. “用户需要探索的方向”在需求收集阶段指本次希望了解的主题和关注重点。围绕它进行引导性询问属于一期需求澄清，不等于二期协同探索执行。喜好引导依据用户描述和回答，工作流定义只约束必要输入检查、适用范围及后续执行规则，不作为固定偏好问卷。
14. **目标用户与初始配置**：目标用户为未参与开发、仅按 quickstart 操作的本机单用户；允许查阅 quickstart 与界面提示，不允许开发人员代操作、使用命令行或直接修改内部数据。初始配置完成指：数据库迁移已至最新版本、数据目录可写、`/health` 的 `execution_available` 为真（Mock 模式或已验证的真实模式）、保留与上限政策已展示并保存。
