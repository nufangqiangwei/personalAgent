# Personal-Agent 项目宪章

## 核心原则

本宪章规定长期适用的工程边界，不定义业务功能、产品范围或交付排期。
“必须”和“禁止”为强制约束；不适用项必须在变更审查中说明理由。

### 一、工作流确定性

- 阶段顺序、状态转移、完成条件、权限、预算和终态必须由显式代码或版本化配置定义。
  模型输出不得直接改变控制规则，也不得绕过输入校验或授权边界。
- 每次执行必须记录有效输入快照、配置与工作流版本，以及模型、工具和运行时的版本或标识。
  用户输入、系统默认值和模型推断必须可区分，不得将推断静默提升为已确认输入。
- 时间、随机数、网络响应和模型输出等非确定性依赖必须通过明确接口注入或记录。
  相同输入、规则版本和外部观测记录下，控制决策与约束校验结果必须一致。
- 模型与工具输出必须通过结构和语义校验才能驱动下一步；无效输出必须进入有界重试或显式失败。
  重试次数、超时和资源预算必须有上限，禁止无界循环。

确定性约束针对执行控制与规则判定，不承诺实时外部数据或模型自然语言逐字一致。

### 二、执行可恢复性

- 执行状态、阶段产物、失败原因及版本关联必须持久化，并定义可验证的状态转换和检查点边界。
  状态更新与对应产物提交必须保持一致，禁止把未完整保存的阶段标记为成功。
- 进程退出、超时、取消或依赖失败后，必须能识别最后有效状态及未完成步骤。
  无法确认完成的操作必须标记为中断或待核验，禁止静默宣告成功。
- 可重试操作必须具备幂等性、去重机制或补偿策略；涉及外部副作用时必须先核验既有结果，
  禁止因重试或恢复重复产生未经授权的副作用。
- 恢复前必须校验输入、配置、状态模式和产物版本的兼容性。
  无法安全恢复时必须停止，并提供可诊断原因及安全重启或人工处置路径。
- 数据迁移与备份方案必须包含恢复步骤，并通过恢复验证后才能承担生产数据保护职责。

可恢复性要求中断可识别、状态可信和处置安全，不强制引入自动续跑或定时调度等产品功能。

### 三、架构解耦

- 领域规则、工作流编排、模型运行时、外部工具、持久化和展示层必须具有明确职责与接口。
  领域规则不得依赖界面实现、框架内部对象或具体供应商协议。
- 模型、工具和存储依赖必须通过适配器接入；接口必须定义输入、输出、错误、超时和取消语义。
  更换外部实现不得要求重写领域规则，适配器必须能够独立进行契约测试。
- 跨层通信必须使用显式数据契约，禁止依靠共享可变全局状态或读取其他模块私有数据通信。
  状态转换由编排层负责，底层适配器不得隐式推进业务状态。
- 新增抽象、基础设施或跨进程边界必须说明当前需求、替代方案与维护成本。
  禁止仅为假设中的未来需求引入通用平台或额外部署组件。

边界隔离使规则可独立验证，并限制框架升级及外部服务变化的影响范围。

### 四、自动化测试

- 每项行为变更必须对应可执行验收条件与适当层级的自动化测试。
  缺陷修复必须先增加可复现缺陷的失败测试，再验证修复；纯文档变更执行文档检查。
- 领域规则与状态机必须具备确定性单元测试；跨模块接口和外部适配器必须具备契约或集成测试。
  关键路径必须覆盖成功、非法输入、依赖失败、超时、取消和中断处置。
- 重试、持久化、迁移或恢复逻辑变更时，必须验证重复执行、部分写入及版本不兼容情形，
  确认不会误报成功或重复产生副作用。
- 默认自动化测试必须使用固定样本与可控的时钟、随机源和外部响应，
  不得依赖真实凭据、付费模型或实时网络才能完成。
  真实依赖验证必须与默认测试分离，明确运行条件和费用边界。
- 合并前必须通过适用的类型检查、静态检查和自动化测试。
  跳过、隔离或失败的测试必须有可追踪原因与处置记录，不得将未运行报告为通过。

测试必须验证可观察行为和工程契约，避免用重复实现细节的断言替代有效保障。

### 五、数据安全

- 必须按最小必要原则收集、保存和传输数据，定义用途、访问权限、保留期限和删除方式。
  向外部模型或工具发送数据前必须检查授权范围，只发送当前操作所需的信息。
- 密钥、令牌和凭据必须由受控配置或密钥存储注入，禁止写入源码、版本库、测试样本或日志。
  日志、错误、导出内容和诊断产物必须脱敏，不得记录可用凭据或不必要的个人敏感信息。
- 外部网页、文件和模型输出必须视为不可信数据，其中的指令不得改变权限或执行策略。
  工具调用必须经过参数、目标范围和权限校验，禁止直接执行不可信文本构造的命令或查询。
- 文件和网络访问必须限制在授权边界内，校验路径与请求目标，防止路径穿越及未授权内部访问。
  远程敏感数据传输必须使用受验证的加密连接。
- 状态、备份和诊断数据必须采用与原始数据相匹配的保护措施。
  安全相关变更必须包含越权访问、敏感信息泄漏或不可信输入处理的验证证据。

## 技术约束

- 技术选型及具体版本由设计文档和依赖清单维护，采用前必须完成兼容性验证。
  不得将尚未验证的技术方案视为既成事实；本宪章不绑定具体业务场景。
- 运行时、包管理器和直接依赖必须明确版本要求，依赖解析必须使用锁文件或等效固定机制。
  构建和测试入口必须可重复执行，不得依赖未记录的机器配置或人工修改第三方包。
- 外部数据、持久化状态和模块边界必须进行运行时校验，不能仅依赖编译期类型。
  契约与存储模式变更必须提供兼容策略；破坏性变更必须提供迁移和失败恢复说明。
- 运行事件必须包含执行标识、阶段标识、状态、时间和结构化错误类别，以关联问题与检查点。
  可观测数据必须遵守脱敏与保留规则，不记录模型内部推理。
- 资源上限和取消信号必须贯穿编排层与适配器；无法即时取消的依赖必须有超时及结果隔离策略，
  禁止让迟到结果覆盖已取消或已终止的状态。
- 框架升级必须通过适配器边界验证，并执行相关契约、状态转换、取消及恢复回归检查。
  不得依赖未经验证的框架行为承担权限控制或数据一致性职责。

## 开发流程

1. **定义变更**：在规格中写明目标、范围、非目标、可验证验收条件和数据影响。
   业务需求归入规格文档，不得通过修改宪章绕过需求评审。
2. **设计与宪章检查**：在计划中逐项检查五项核心原则，记录状态模型、模块边界、失败处置、
   测试策略和安全边界；不适用项必须说明依据，偏离项必须按治理规则处理。
3. **拆分任务**：按依赖顺序拆成可审查的小步，明确产物、验证方式与适用的回退方法。
   契约、迁移、异常路径和测试工作必须显式列入任务，不得只列正常路径实现。
4. **实施验证**：实现与测试同步推进，使用固定样本验证控制逻辑，对新增依赖单独完成集成验证。
   仅修改当前变更所需文件，禁止捎带无关重构。
5. **审查合并**：提交变更说明、测试结果、未解决限制及适用的迁移或回退说明。
   项目维护者必须核查宪章符合性；未通过强制质量检查或未经处理的偏离不得合并。
6. **交付复盘**：涉及运行环境或数据变化时，交付前验证部署配置与恢复路径。
   缺陷必须记录根因并补充回归保障，长期规则调整必须作为独立宪章修订审查。

## 治理规则

- 本宪章是项目工程治理的最高内部基线。规格、计划、任务、实现和操作文档必须与其一致。
  冲突必须记录并修正，禁止静默忽略；具体功能与排期由相应需求文档维护。
- 修订必须说明动机、条款差异、影响范围、迁移安排和版本变化理由，经项目维护者审阅批准后生效。
  首次建立版本为 1.0.0，批准日期为 2026-10-19。
- 版本遵循语义化规则：删除或不兼容地重定义治理原则增加主版本；新增原则、章节或实质扩展约束
  增加次版本；仅澄清措辞且不改变义务增加修订版本。每次修订更新最后修订日期，首次批准日期不变。
- 每份实施计划和每次合并审查必须提供宪章符合性结论与验证依据。
  新条款影响既有实现时必须记录差距、负责人和整改期限，不得假定存量自动合规。
- 临时例外必须记录受影响条款、必要性、替代方案、风险、补偿措施、负责人和到期日期，
  由项目维护者明确批准；到期必须恢复合规或重新审查，不得形成无期限豁免。
  例外不得授权泄露凭据、越权访问或伪造验证结果。
- 修订对依赖文档的影响必须在评审中明确，后续命令读取最新宪章并完成相应一致性检查。
  文件顶部同步影响报告仅供本次审阅，提交前移除，不属于长期治理条款。
