# 个人信息收集与处理助理｜产品需求文档

> 状态：需求初稿。本文描述产品行为与验收要求，不限定框架、协议、插件机制或存储方式。首期范围按个人使用、少量预设工作流拟定。

## 1. 项目目标

为用户提供一个按个人要求收集、筛选和整理信息的助理。用户选择工作流并提供任务目标、约束和偏好后，系统执行信息收集与处理，交付带有来源、便于比较和使用的结果。

项目不限定于测试案例。旅游探索是测试使用案例，后续可以扩展到求职调研、商品比较等任务。不同任务共享输入、执行、信息整理和结果交付能力，各自定义需要搜集的信息、评价标准与输出内容。

产品包含两种工作模式：

1. **固定工作流模式**：按照预先定义的步骤和规则查询指定方向的信息，再按用户偏好整理并交付。首期完成该模式。
2. **工作流探索模式**：在用户给定的目标和范围内探索执行方法，记录步骤、选择理由、结果及用户反馈，后续将有效路径整理为可复用工作流。该模式不纳入首期。

## 2. 首期使用场景与范围

### 2.1 目标用户

需要反复搜集和比较信息、希望减少手工整理工作，并且对结果有明确偏好的个人用户。

### 2.2 使用流程

选择预设工作流 → 填写任务与偏好 → 检查必要输入 → 执行收集和整理 → 查看结果及来源。

首期重点验证：同一个预设工作流能在不同任务输入下重复执行，结果符合用户约束，且用户可以核查重要信息的来源。

### 2.3 范围边界

- 首期至少跑通一个预设工作流，以旅游信息探索作为候选验收案例；不要求同时完成多个领域。
- 支持用户明确填写偏好，并保存为后续可复用的默认值；本次填写的要求优先。
- 提供结果与建议，不执行预订、支付、投递、对外发送等后续行动。
- 不要求首期完成通用工作流编辑器、自动生成工作流、多用户协作、定时执行或中断后的自动续跑。
- 不承诺访问所有信息平台，也不承诺获取实时数据；信息不足时必须说明。

## 3. 首期产品功能

### F01. 预设工作流选择

用户可以查看并选择可用工作流。每个工作流应说明用途、必要输入和预期产出。

固定工作流应定义：输入项、主要处理步骤、信息范围、筛选规则、输出格式和完成条件。执行时允许根据输入调整搜索词和候选数量，但不得擅自改变任务目标或扩大范围。

**验收要求：** 同一工作流可以使用不同输入重复执行；用户在执行前能够知道需要提供什么、最终会得到什么。

### F02. 任务输入与必要信息检查

用户可以输入目标、硬约束、软偏好和输出要求。硬约束用于排除不合格结果，软偏好用于排序或说明取舍。

开始执行前检查工作流要求的必要信息。缺少关键输入时提示补充；非关键输入可采用明确展示的默认值，不得将假设写成用户已确认的事实。

**验收要求：** 必要输入缺失时不会直接开展依赖该输入的工作；结果能对应到本次任务的目标与约束。

### F03. 显式偏好管理

用户可以填写、查看、修改和删除已保存的偏好。系统区分默认偏好与本次要求，并使用与当前任务相关的偏好。

首期由用户明确决定哪些内容需要长期保存，不自动从全部聊天或历史行为推断长期偏好。修改本次要求不应自动覆盖默认偏好。

**验收要求：** 已保存偏好可用于后续任务；本次要求与默认偏好冲突时，以本次要求为准；删除的偏好不再用于新任务。

### F04. 信息搜集

根据工作流和用户输入，在已支持的信息来源中查询并读取相关内容。根据任务需要搜集多个来源，不以搜索结果摘要直接代替所有关键事实的核查。

记录来源名称、链接、获取时间，以及能够获得的发布时间或更新时间。来源无法访问、查询失败或信息不足时，应标记缺失情况，并在已有信息足够时继续交付部分结果。

**验收要求：** 结果中的重要外部事实能追溯到来源；无法获得的信息不会被虚构补齐；用户能看到影响结果完整性的搜集失败。

### F05. 信息整理与筛选

对材料进行去重、归类和必要字段提取，依据硬约束筛选候选项，并按工作流评价标准及个人偏好组织结果。

区分可核查事实、来源中的主观评价和系统推断。对发现的来源冲突、过期信息或无法确认的内容进行标注，不要求首期自动发现所有错误或矛盾。

**验收要求：** 明确违反硬约束的候选项不能作为合格推荐；关键条件未知的候选项需标为待确认；不能因信息缺失而默认符合要求。

### F06. 结果交付

以便于阅读的报告、列表或对比表交付结果。格式由工作流定义，首期不要求同时支持多种文件导出。

结果至少包含：

- 本次任务目标和采用的主要约束；
- 筛选或整理后的内容；
- 推荐、排序或排除的主要理由；
- 重要信息对应的来源；
- 尚未确认的条件、信息缺口和必要的后续核查事项。

没有足够合格结果时，可以减少结果数量或返回“未找到符合条件的结果”，不得为了凑数放宽硬约束。

**验收要求：** 用户能理解结果为何符合自己的要求，并能通过来源核查重要结论；未完成的部分不能被表述为已完成。

### F07. 基本任务状态与失败反馈

用户可以知道任务是否正在执行、已经完成或执行失败。执行期间至少展示当前主要阶段，如搜集、整理、生成结果。

任务应有执行范围或时长上限，避免无限搜索。发生失败或达到上限时，说明哪些工作已完成、哪些没有完成；允许用户重新发起任务。

**验收要求：** 任务不会无提示地长期停留在运行中；失败有可理解的说明；部分结果与完整结果有明确区分。

## 4. 特定任务需求：旅游信息探索案例

本节仅描述旅游任务的规则，不作为所有工作流的通用要求。首期案例先以“用户已经确定目的地”为输入；“帮助用户决定去哪里”作为扩展。

### 4.1 输入

- 目的地和出行日期或大致时间范围；
- 可用天数、预算及交通方式；
- 感兴趣和不感兴趣的体验类型；
- 对人群、步行强度和出行节奏的要求；
- 是否探索周边，以及可接受的单程交通时间。

具体必填项由工作流明确，不能要求用户为与本次任务无关的字段提供信息。

### 4.2 处理与输出要求

1. 搜集目的地可游玩点及活动，解释其与个人偏好的关系。
2. 在支持的信息来源内查询开放、预约、时间或季节限制等关键条件。
3. 根据可获得证据说明可能的拥挤情况，提供错峰时段或替代体验；没有客流数据时不得承诺现场人少。
4. 搜集容易踩坑、不值得额外投入或不适合该用户的事项，区分客观限制与主观评价。
5. 用户启用周边探索时，按约定范围补充体验，并说明交通成本和额外前往的理由。
6. 输出候选项目、推荐理由、预计时间及费用（能查到时）、注意事项和来源。估算数据需明确标注。

### 4.3 案例验收

给定“某目的地、三天、不自驾、喜欢自然、希望避开拥挤”的输入：

- 推荐理由能够关联到自然体验和人群偏好；
- 交通条件与不自驾的约束一致，无法确认的项目明确标注；
- 人群判断有依据或不确定性说明；
- 关键注意事项附有来源；
- 周边项目不超出用户规定的探索范围；
- 不因查不到信息而生成未经支持的开放时间、费用或预约规则。

## 5. 后续扩展功能

以下内容保留为后续方向，不作为首期完成条件。

| 功能 | 用户价值与预期行为 |
|---|---|
| 根据反馈调整结果 | 用户指出不合适的内容后，修改相关部分并尽量保留有效信息 |
| 历史任务与结果复用 | 查阅旧结果，复用输入或重新查询过期信息 |
| 辅助提炼长期偏好 | 从用户主动提供的经历和反馈中提出偏好建议，经确认后保存 |
| 更多任务工作流 | 增加目的地发现、求职调研、商品比较等领域任务 |
| 工作流探索模式 | 围绕目标尝试步骤，记录操作、选择理由、依据、结果与反馈 |
| 探索结果固化 | 将有效探索过程整理为工作流草稿，明确可变输入、规则和完成条件，经用户确认后复用 |

探索记录应面向可审查的行动和决策摘要，不要求保存模型内部逐字推理。固化后的工作流需要在新的输入上验证，不能只因一次任务成功就视为通用流程。

## 6. 首期整体验收标准

1. **流程完整**：用户能完成选择工作流、填写输入、执行任务和查看结果的全过程。
2. **可重复使用**：至少一个预设工作流能在不同输入下运行，不依赖预先写好的固定答案。
3. **偏好生效**：更改与任务相关的偏好后，筛选、排序或解释能体现合理变化。
4. **约束遵守**：明确违反硬约束的内容不会混入合格推荐；未知条件有标记。
5. **来源可查**：重要外部事实有对应来源，事实、评价和推断不会混为一谈。
6. **异常可见**：能够处理缺少输入、来源失败、无合格结果及执行超时等情况，并给出明确反馈。
7. **范围可控**：首期可在个人使用场景下完成上述流程，不以完成后续扩展功能为前提。

## 7. 后续需要细化的配置

以下项目在选择首个工作流和信息来源后确定，不影响当前功能范围：

- 首个正式验收工作流及其必填项；
- 支持的信息来源及访问失败时的处理顺序；
- 每次任务的搜索范围、结果数量和执行时间上限；
- 不同类型信息的时效要求；
- 结果质量评估样例及可接受的执行成本。
