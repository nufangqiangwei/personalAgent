## 1. 一期定义与目标

### 1.1 一期做什么

一期交付**固定工作流模式**的完整闭环：用户选择一个预设工作流 → 填写任务目标与偏好 → 系统执行信息收集与整理 → 交付带来源、可核查、区分「推荐 / 待确认 / 排除」的结果。

一期结束时，用户可以在本机独立完成上述全过程，且结果在**换一组输入后依然成立**，而不是靠预置答案。

### 1.2 一期不做什么

| 不做项 | 说明 |
|---|---|
| 工作流探索模式 | 围绕目标自主尝试步骤、记录探索路径，全部推迟到后续 |
| 工作流自生成 / 通用编辑器 | 首期工作流由代码注册，用户不能提交自定义流程 |
| 多领域工作流 | 只交付旅游一个领域；求职调研、商品比较等不在一期 |
| 历史任务检索与复用、自动续跑、定时执行 | 一期只持久化当前任务用于交付与异常识别 |
| 多用户与协作 | 单用户、本机部署 |
| 结果修改与反馈迭代 | 用户指出不合适内容后局部修改，属后续功能 |
| 任意文件导出 | 报告在页面内交付，不承诺多格式导出 |
| 预订、支付、投递、对外发送 | 只给建议，不产生任何对外副作用 |
| 登录态平台、验证码绕过 | 只读公开可访问网页 |

### 1.3 一期成功指标

| 维度 | 指标 | 目标 |
|---|---|---|
| 流程完整性 | 用户独立完成"选工作流 → 填输入 → 执行 → 看结果"的比例 | 100%（验收样例全通过） |
| 可重复性 | `travel.destination.v1` 在 ≥3 组不同输入下成功执行 | ≥3 组，且无硬编码答案 |
| 约束遵守 | 明确违反硬约束的候选进入合格推荐的数量 | 0 |
| 来源可查 | 报告中关键外部事实具备可定位来源的比例 | 100%（人工抽查通过） |
| 异常可见 | 超时、来源失败、无合格结果、重启中断均落到可解释终态 | 100% |
| 成本可控 | 单任务费用与调用次数不超上限，且可查看 | 100% |

> 联网来源质量（有效来源比例、字段缺口率）与成本阈值在一期首轮基线测量后冻结，**不承诺未测量的成功率**。

## 2. 目标用户与核心场景

### 2.1 目标用户

需要反复搜集和比较信息、希望减少手工整理工作、并且对结果有明确偏好的个人用户。典型特征：

- 会自己搜索，但不喜欢在多个标签页之间做交叉核对与整理；
- 对结果有偏好（体验类型、人群、节奏、预算），但不愿每次都重述；
- 需要知道结论从哪来，对"看起来很确定但没出处"的内容不信任。

### 2.2 目标用户不包含

需要团队协作、需要对外发布、需要系统代为下单或提交的用户。

### 2.3 关键用户故事

| 编号 | 故事 | 对应需求 |
|---|---|---|
| US-01 | 我想先看清楚有哪些工作流、各自要什么输入，再决定用哪个 | F01 |
| US-02 | 我想一次填清这次的要求（目的地、天数、交通、喜好、限制），并在开始前知道系统会遵守什么 | F02 |
| US-03 | 我不想每次重复填写同样的偏好，但这次的特殊要求必须优先 | F03 |
| US-04 | 我想知道系统读了哪些页面、哪条信息没查到，而不是给我一个笼统结论 | F04 |
| US-05 | 我想知道每个推荐为什么适合我，以及哪些因为不满足硬条件被排除 | F05、F06 |
| US-06 | 我希望任务卡住或失败时能明确告诉我已完成到哪一步，并能重新发起 | F07 |

## 4. 业务流程与信息架构

### 4.1 主流程

```text
[1] 选择工作流
     ↓  查看用途 / 必填输入 / 预期产出
[2] 填写任务与偏好
     ↓  本次输入 + 已保存偏好 + 工作流默认值 三者分列展示
[3] 执行前检查
     ↓  缺失必填 → 阻塞并提示补充；非必填 → 使用明示默认值
[4] 确认并开始
     ↓  展示本次采用的硬约束、默认值、预算与范围
[5] 执行中
     ↓  阶段进度：搜集 → 关键条件核查 → 提取整理 → 筛选排序 → 生成报告
[6] 查看结果
     ↓  推荐 / 待确认 / 排除及原因 / 来源与缺口
[7] 重新发起（如需）
```

### 4.2 页面结构

| 页面 | 内容 | 覆盖需求 |
|---|---|---|
| 工作流列表 | 工作流名称、用途、必填输入、预期产出、预计耗时与预算 | F01 |
| 任务表单 | 任务目标、硬约束、软偏好、输出要求；展示每个字段的取值来源（本次 / 偏好 / 默认值） | F02、F03 |
| 执行前确认 | 缺失项与冲突提示、有效输入预览、本次硬约束清单、范围与上限 | F02 |
| 偏好管理 | 已保存偏好的查看、修改、删除；标注适用工作流与更新时间 | F03 |
| 任务进度 | 当前状态、当前阶段、已完成阶段、剩余预算提示、失败或部分完成说明 | F07 |
| 结果报告 | 六段式报告 + 来源清单 + 缺口清单 | F06 |

### 4.3 任务状态与阶段的双层展示

- **状态**（面向用户的任务终态）：`等待补充输入 → 排队 → 运行中 → 完成 / 部分完成 / 失败`
- **阶段**（执行细节）：`搜集 / 核查 / 整理 / 生成`

规则：

1. "无匹配结果"是**成功执行**后的结果类型，不是失败；
2. 因失败或预算耗尽留下未完成检查的，是**部分完成**，不得显示为完成；
3. 部分完成必须携带：未完成阶段、失败来源、条件缺口、停止原因；
4. 没有任何可交付产物时才是**失败**。

## 5. 功能需求

### F01 预设工作流选择

**目标**：用户在执行前就能知道需要提供什么、最终会得到什么。

**需求**

1. 列表展示可用工作流，每项至少包含：名称、一句话用途、必填输入清单、预期产出形态、首期覆盖范围与不覆盖范围。
2. 工作流定义（产品可见层面）必须包含：输入项、主要处理步骤、信息范围、筛选规则、输出格式、完成条件。
3. 执行时允许根据输入调整搜索词和候选数量，**不得擅自改变任务目标或扩大范围**。
4. 首期只注册一个正式工作流 `travel.destination.v1`；其余领域不以"占位工作流"形式出现在列表里。

**验收要求**

| 编号 | 用例 | 通过标准 |
|---|---|---|
| F01-AC1 | 同一工作流以 ≥3 组不同目的地/时间输入执行 | 每次都能跑通，结果随输入变化 |
| F01-AC2 | 查看工作流说明后开始填写 | 用户不需要额外询问即可知道哪些字段必填 |

---

### F02 任务输入与必要信息检查

**目标**：必要信息不全时不开展依赖该信息的工作；所有假设可见。

**输入分类**

| 类别 | 作用 | 未填写时行为 |
|---|---|---|
| 硬约束 | 排除不合格结果 | 必填项缺失 → 阻塞；可选项缺失 → 不参与筛选 |
| 软偏好 | 排序或解释取舍 | 使用明示的工作流默认值，并标记为默认 |
| 输出要求 | 结果数量、关注重点 | 使用工作流默认输出格式 |

**需求**

1. 开始执行前的检查项：必填字段完整性、字段间冲突、取值范围合法性、偏好与本次输入的冲突。
2. 必填缺失 → 不创建任务，明确提示缺哪一项及其用途。
3. 非必填采用默认值时，必须在执行前确认页**明示默认值及其来源**，不得把假设写成用户已确认的事实。
4. 执行时生成**不可变输入快照**，逐字段标注来源：`本次输入 / 已保存偏好 / 工作流默认值`。
5. 同一任务重复提交需幂等，不产生重复任务（一期用户侧表现为"不会重复执行"）。

**验收要求**

| 编号 | 用例 | 通过标准 |
|---|---|---|
| F02-AC1 | 缺目的地 / 时间 / 交通方式 | 不发起任何依赖该输入的搜集调用 |
| F02-AC2 | 只填部分非必填项 | 确认页列出所有采用的默认值；报告中的结论能对应本次目标与约束 |
| F02-AC3 | 填写互相冲突的条件（如"不走路"+"徒步路线"） | 执行前提示冲突并要求用户确认取舍 |

---

### F03 显式偏好管理

**目标**：偏好可长期复用，但绝不覆盖或冒充本次要求。

**需求**

1. 用户可查看、修改、删除已保存偏好；每条偏好标注适用的工作流/范围与更新时间。
2. 优先级采用**字段级合并**：
   `本次明确填写值 > 已保存且与当前工作流相关的偏好 > 展示的工作流默认值`
3. **显式清空 ≠ 未填写**：用户清空某字段，不得被已保存偏好填回。
4. 本次修改**不自动写入长期偏好**；长期保存只能通过偏好管理界面的独立操作完成。
5. 删除偏好后，新任务不得读取旧值；已运行任务按当时快照解释结果。
6. 首期不自动从聊天或历史行为推断长期偏好。

**验收要求**

| 编号 | 用例 | 通过标准 |
|---|---|---|
| F03-AC1 | 保存偏好 → 新任务使用 | 新任务自动带入该偏好并标注来源为"已保存偏好" |
| F03-AC2 | 本次要求与默认偏好冲突 | 以本次要求为准，且报告中体现该取值 |
| F03-AC3 | 本次显式清空某字段 | 该字段为空，不被偏好填回 |
| F03-AC4 | 删除偏好 → 新任务 | 旧值不出现 |

---

### F04 信息搜集

**目标**：重要外部事实可追溯到来源；查不到就说查不到。

**需求**

1. 按工作流与用户输入，在**已支持的信息来源**内查询并读取内容；不以搜索摘要代替关键事实的核查。
2. 每条来源记录：来源名称、链接（最终 URL）、获取时间、可获得的发布时间或更新时间、来源类型。
3. 来源策略按信息类型区分优先级：
   - 开放、预约、票价：优先官方公告；
   - 公共交通：优先运营方或授权路线信息；
   - 拥挤与体验评价：允许近期公开游记，但保留作者观点与时间，不据此承诺现场人少。
4. 一项任务需覆盖多个来源；单站点失败不影响整体继续。
5. 失败处理顺序：**有限重试 → 其他来源 → 标记缺口**。
6. 出现以下情况必须标记缺失并影响完整性提示：来源无法访问、查询失败、信息不足、内容被截断。
7. 已有信息足够时，继续交付**部分结果**，并说明缺口影响的字段。
8. 时效策略：开放/预约/票价/交通优先本次重新读取，跨任务缓存最长 24 小时；一般体验介绍可缓存 7 天。刚抓取的旧公告不得判为最新规则。
9. 未配置有效搜索服务时**明确报错**，不得以模型记忆模拟联网结果。

**验收要求**

| 编号 | 用例 | 通过标准 |
|---|---|---|
| F04-AC1 | 任取报告中的关键事实 | 能定位到具体原文片段 |
| F04-AC2 | 手工构造部分网页读取失败 | 报告中可见失败来源与受影响的字段，其余内容仍交付 |
| F04-AC3 | 搜索服务不可用 | 任务明确失败或部分完成并说明原因，不产生"虚拟联网"内容 |
| F04-AC4 | 抓取到已过期公告 | 相关条件降为待确认，不作为最新规则使用 |

---

### F05 信息整理与筛选

**目标**：去重、归类、提取必要字段，按硬约束筛选，按偏好排序，事实与评价与推断分离。

**需求**

1. 对材料去重、归类，提取工作流所需的必要字段。
2. 区分三类信息并显式标注：
   - **可核查事实**（有来源原文支持）
   - **来源中的主观评价**（标注来源主体与时间）
   - **系统推断或估算**（显示"推断/估算"）
3. **硬约束三态判定**：每条硬约束返回 `pass / fail / unknown`，并附规则 ID、证据 ID、原因。
   - 任一硬约束 `fail` → 进入**排除项**，不得进入合格推荐；
   - 无 `fail` 但至少一个关键硬约束 `unknown` → 进入**待确认项**；
   - 全部适用硬约束 `pass` → 进入**合格推荐**。
4. 不得因信息缺失而默认符合要求（"查不到"不等于"满足"）。
5. 对来源冲突、过期信息、无法确认的内容标注；不要求一期自动发现所有错误或矛盾。
6. 软偏好排序：按工作流定义维度评分（体验匹配、交通便利、步行/节奏适配、拥挤风险），权重来自显式偏好与展示的工作流默认值，保留每项理由与证据。
   - 未知维度不赋予正向优势，使用保守默认分并显示证据缺口；
   - 合格项与待确认项**分别排序**；
   - 不能用高偏好分抵消硬约束的未知或不通过。
7. 没有合格项时：交付"未找到符合条件的结果"，保留待确认项供用户核查，**不降低约束凑数**。

**验收要求**

| 编号 | 用例 | 通过标准 |
|---|---|---|
| F05-AC1 | 候选明确违反硬约束 | 出现在排除项，附具体规则 ID 与原因，不出现在推荐中 |
| F05-AC2 | 关键条件未知（如交通方案未知） | 标为待确认；不因地点临近而判为可达 |
| F05-AC3 | 来源之间存在冲突 | 冲突被标注，冲突项状态降级为待确认 |
| F05-AC4 | 全部候选不合格 | 返回"未找到符合条件的结果"，硬约束未被放宽 |

### F06 结果交付

**目标**：用户能理解结果为何符合自己的要求，并能通过来源核查重要结论。

**报告结构（六段式，顺序固定）**

| 段 | 内容 | 必填 |
|---|---|---|
| 1. 任务摘要 | 本次目标、采用的主要硬约束与软偏好、每项取值来源 | 是 |
| 2. 合格推荐 | 推荐项、预计时间与费用（能查到时，估算需标注）、推荐理由、来源 | 是（可为空集） |
| 3. 待确认项 | 未确认的条件、缺什么证据、建议如何核查 | 是（可为空集） |
| 4. 排除项及原因 | 被硬约束排除的候选与具体原因 | 是（可为空集） |
| 5. 注意事项与避坑 | 区分客观限制与主观评价 | 是 |
| 6. 来源与缺口 | 来源清单（名称、链接、获取时间）与本次信息缺口、后续核查事项 | 是 |

**需求**

1. 交付形态：便于阅读的报告 + 候选对比列表。输出格式由工作流定义，一期不要求多种文件导出。
2. 结果数量：目标 5–8 个合格项，不足允许不足，不凑数。
3. 没有足够合格结果时，减少数量或返回"未找到符合条件的结果"。
4. 未完成的部分**不得表述为已完成**；部分结果与完整结果必须明确区分。
5. 报告中所有链接从证据库生成，不由模型拼接；外部链接协议受限并做转义。
6. 阶段进度与结果页不得展示模型内部推理内容。

**验收要求**

| 编号 | 用例 | 通过标准 |
|---|---|---|
| F06-AC1 | 完整报告检查 | 六段齐全；推荐、待确认、排除、来源与缺口分区明确 |
| F06-AC2 | 抽查推荐理由 | 理由能关联到用户偏好与证据 |
| F06-AC3 | 部分完成的任务 | 页面明确标注未完成部分与原因，不显示为完成 |

---

### F07 任务状态与失败反馈

**目标**：任务不会无提示地长期停留；失败可理解；部分结果与完整结果可区分。

**需求**

1. 用户可看到任务是否正在执行、已完成或失败；执行期间至少展示当前主阶段（搜集、核查、整理、生成）。
2. 状态变更通过事件推送（SSE）展示，提供轮询兜底；SSE 断开不取消任务；重新进入页面先读任务快照，再从最后事件序号继续。
3. 任务应有执行范围与时长上限，避免无限搜索：
   - 达到**搜集期限**：停止新增检索，以已验证数据交付部分结果；
   - 达到**总期限**：取消在途请求，输出确定性兜底报告，不再依赖模型收尾。
4. 失败或达到上限时，说明哪些工作已完成、哪些没有完成、为什么停止。
5. 允许用户重新发起任务；一期**不自动续跑**。
6. 应用重启后，遗留运行任务标记为中断失败，保留已有产物，允许重新发起。
7. 一期只允许一个活跃任务；超出时明确提示等待，不形成无界队列。

**验收要求**

| 编号 | 用例 | 通过标准 |
|---|---|---|
| F07-AC1 | 网络超时 / 模型挂起 / 达到上限 / 进程重启 | 均收敛到终态，且有可理解说明 |
| F07-AC2 | 执行中关闭页面再打开 | 状态不丢失，从最后事件序号继续 |
| F07-AC3 | 已有活跃任务时再发起 | 明确提示等待，不产生并发执行 |

## 6. 旅游工作流领域需求（`travel.destination.v1`）

本节只约束旅游工作流，不作为所有工作流的通用要求。一期案例以"用户已经确定目的地"为输入；"帮助用户决定去哪里"属扩展，不在一期。

### 6.1 输入项

| 字段 | 必填性 | 说明 |
|---|---|---|
| 目的地 | 必填 | 已确定 |
| 出行日期或大致时间范围 | 必填 | 精确日期与大致月份的处理不同（见 6.4） |
| 可用天数 | 必填 | 影响候选数量与节奏 |
| 交通方式 | 必填 | 如"不自驾"是硬约束 |
| 预算 | 可选 | 允许明确选择"不作为筛选条件"；一旦填写为硬预算，必须明确币种、每人或总额、包含门票/市内交通等哪些支出 |
| 体验类型（感兴趣/不感兴趣） | 可选 | 软偏好，驱动推荐理由 |
| 人群、步行强度、出行节奏 | 可选 | 软偏好 |
| 是否探索周边 + 可接受的单程交通时间 | 可选 | 周边探索默认关闭，并在执行前展示；开启后必须提供单程交通时间上限 |

规则：

1. 必填项由工作流明确定义，**不得要求用户提供与本次任务无关的字段**。
2. "希望避开拥挤"默认是**软偏好**；只有用户明确指定的可测限制才能作为硬约束。
3. 不把"安静""轻松"等描述转换成未经确认的数值阈值。
4. 若需核查交通时间，还需明确市内出发参考点，可采用页面展示的"目的地主要交通枢纽"作为默认值并标注来源为默认值；没有参考点的精确交通时间不能作为已验证事实。

### 6.2 处理与输出要求

1. 搜集目的地可游玩点及活动，并解释其与个人偏好的关系。
2. 在支持的信息来源内查询开放、预约、时间或季节限制等关键条件。
3. 根据可获得证据说明可能的拥挤情况，提供错峰时段或替代体验；**没有客流数据时不得承诺现场人少**。
4. 搜集容易踩坑、不值得额外投入或不适合该用户的事项，区分客观限制与主观评价。
5. 用户启用周边探索时，按约定范围补充体验，说明交通成本与额外前往的理由。
6. 输出候选项目、推荐理由、预计时间及费用（能查到时）、注意事项和来源；估算数据必须标注。

### 6.3 案例验收

给定输入："某目的地、三天、不自驾、喜欢自然、希望避开拥挤"：

| 编号 | 检查点 |
|---|---|
| T-AC1 | 推荐理由能关联到自然体验与人群偏好 |
| T-AC2 | 交通条件与"不自驾"约束一致；无法确认的项目明确标注 |
| T-AC3 | 人群判断有依据或明确的不确定性说明 |
| T-AC4 | 关键注意事项附有来源 |
| T-AC5 | 周边项目不超出用户规定的探索范围；周边关闭时完全不出现在结果中 |
| T-AC6 | 不因查不到信息而生成未经支持的开放时间、费用或预约规则 |

附加边界样例：周边时间超限、交通未知、旧预约公告、来源冲突、全部候选不合格。

### 6.4 日期精度规则

| 输入形态 | 可判断 | 必须标注为待确认 |
|---|---|---|
| 精确日期 | 当日开放、预约、班次状态（有官方来源时） | 无官方来源的条件 |
| 大致月份/季节 | 季节性条件、气候与旺季判断 | 具体日期的开放与预约状态 |

### 6.5 输出边界

输出是**游玩候选与比较**，不默认升级为完整行程排程，也不包含住宿与大交通的旅行预算优化。

## 7. 非功能需求

### 7.1 执行预算与范围（首期初始值，待 P0 标定）

| 项目 | 初始值 | 可配置 | 用户可见 |
|---|---|---|---|
| 总时长 | 8 分钟，其中最后 60 秒保留给校验与交付 | 是（上限受控） | 建议可见 |
| 搜索调用 | ≤ 10 次 | 是 | 是（摘要） |
| 正文读取 | ≤ 24 次，每页约 20,000 字符上限并标注截断 | 是 | 是（摘要） |
| 候选数 / 推荐数 | ≤ 15 个候选，目标 5–8 个合格项 | 是 | 是 |
| 模型请求 | ≤ 16 次（含修复与重试） | 是 | 否 |
| 模型累计 token | 初始累计上限 100,000 | 是 | 否 |
| 单次搜索/读取超时 | 20 秒 | 是 | 否 |
| 单次模型超时 | 90 秒，且不超过剩余任务期限 | 是 | 否 |
| 工具并发 | ≤ 3，单站点另有限流 | 是 | 否 |
| 失败重试 | 同一请求最多额外重试 1 次，仍计入总预算 | 是 | 否 |
| 单任务金额上限 | 【待定】P0 实测后设定 | 是 | 是 |

规则：

1. 所有模型阶段、工具调用与修复请求**共用一个预算账本**，不能只靠提示词限制次数。
2. 上线配置必须具备有效上限；**不能把未知费用显示为零**。
3. 预算是安全阀，不是性能承诺。

### 7.2 性能与响应

| 项 | 要求 |
|---|---|
| 页面首屏 | 本机环境下 ≤ 2 秒 |
| 任务创建后首个进度事件 | ≤ 2 秒内出现 |
| 进度推送延迟 | ≤ 1 秒 |
| 报告页渲染 | 本机环境下 ≤ 2 秒 |

### 7.3 安全与数据保护

1. 系统只绑定本机地址；页面写操作校验来源并使用会话令牌。
2. 模型密钥与搜索密钥只留在服务端，不进入网页脚本、模型提示或业务日志。
3. 网页内容按**不可信材料**处理：页面中的"忽略原指令""读取密钥"等文本不能改变工作流、工具权限和用户目标。
4. 一期不挂载模型可用的 shell、任意文件访问、插件安装或代码执行能力。
5. 网页读取限制 HTTP/HTTPS，拦截本机、内网与云元数据地址；对 DNS 解析与重定向逐跳校验；限制响应大小、超时与内容类型。
6. 报告对网页 HTML 与模型文本转义，链接使用安全协议白名单。
7. 只保存与报告相关的必要证据片段与内容哈希；完整正文作为有限期缓存。
8. 隐私偏好只把当前任务必需部分传给模型；搜索词不包含无关个人信息。

### 7.4 可观测性与成本

1. 每次任务记录并展示：耗时、搜索次数、读取次数、模型调用次数、token 用量、估算费用。
2. 记录版本指纹（Harness/SDK/插件/工作流定义版本、费率版本），便于复现。
3. 业务日志只记录工具动作、阶段结果、错误、用量与决策摘要；不展示模型内部推理。
4. 数据保留期：证据缓存与任务记录保留时长【待定】，需在 P0 明确本地访问范围与保留期。

### 7.5 兼容与运行环境

- 首期按当前 Windows 环境验证，不将 WSL 作为必需条件。
- 单用户、单机部署，本地数据可备份、可检查。

## 8. 界面与交互要求

### 8.1 执行前

- 展示本次采用的硬约束清单，以及每个字段的取值来源（本次 / 已保存偏好 / 默认值）。
- 展示范围与上限：周边是否开启、候选数量、时间上限、预算上限。
- 缺失必填项时，开始按钮不可用并说明缺哪一项。

### 8.2 执行中

- 展示当前阶段与已完成阶段，不展示内部推理。
- 展示预算消耗概览（已用搜索次数/读取次数、剩余时间）。
- 允许用户停止任务；停止后进入明确的终态并按部分完成处理（有产物时）。

### 8.3 结果页

明确分区：**推荐 / 待确认 / 排除及原因 / 来源与缺口**。

- 推荐项：理由、预计时间与费用（标注估算）、注意事项、来源链接。
- 待确认项：缺什么、为什么不能确认、建议如何核查。
- 排除项：具体违反哪条硬约束。
- 来源与缺口：来源清单 + 本次未能获取的信息清单。

### 8.4 文案要求

- 事实、评价、推断三类表述必须可区分（推断需带"推断/估算"标记）。
- 不得使用"保证""现场人少""一定开放"等无法确认的承诺式表述。
- 部分完成时使用明确措辞说明未完成部分。

## 10. 验收方案

### 10.1 需求追踪表

| 需求 | 验收方式 | 通过标准 |
|---|---|---|
| F01 工作流选择 | 同一版本以 ≥3 组不同目的地/时间输入执行 | 全部跑通且结果随输入变化 |
| F02 必要输入 | 缺目的地、时间或交通方式 | 不发起任何依赖调用 |
| F03 偏好 | 本次覆盖默认；显式清空；删除后新任务不使用旧值 | 三项均通过 |
| F04 信息搜集 | 关键事实可定位原文；摘要不冒充核查；网页失败可见 | 抽查 100% 可定位 |
| F05 筛选整理 | fail 不混入推荐；unknown 单独展示；冲突与估算有标记 | 0 例违规进入推荐 |
| F06 结果交付 | 条件、理由、来源、缺口齐全；无结果不凑数 | 六段齐全，无凑数 |
| F07 任务状态 | 网络超时、模型挂起、达到上限、进程重启 | 均收敛到终态 |

### 10.2 旅游重点样例矩阵

| 样例 | 关注点 |
|---|---|
| 三天 / 不自驾 / 喜欢自然 / 避开拥挤，周边关闭 | 主路径与偏好生效 |
| 同上 + 周边开启且单程上限给出 | 周边范围与交通成本说明 |
| 周边开启但候选超出单程上限 | 超限项被排除或标待确认 |
| 交通方案未知 | 不判定可达，标待确认 |
| 命中旧预约公告 | 降为待确认，不作为最新规则 |
| 两个来源冲突 | 冲突标注 + 降级 |
| 全部候选不合格 | 返回"未找到符合条件的结果" |

> 日期与预算按表单规则补全；不把需求案例的简写当作完整输入。

### 10.3 验收方法

1. **固定样本回归**：确定性规则（硬约束三态、排序、引用校验、报告结构）用固定网页样本回归，可重复执行。
2. **代码全量检查**：结构化字段与引用链由代码检查，不依赖人工。
3. **真实联网人工抽查**：抽查关键事实是否被原文支持，记录有效来源比例、字段缺口、任务耗时、调用次数与实际费用。
4. **重复运行判定**：不要求文案完全一致，要求**约束与证据规则稳定**。

### 10.4 P0/P1 硬性通过条件

1. 验收样例中**无明确违规候选进入合格推荐**；
2. **无伪造引用**与未经标注的关键估算；
3. 所有异常样例具有**可解释终态**。

联网质量与成本阈值在首轮基线测量后冻结；未测量时不承诺成功率。

## 附录 C：术语表

| 术语 | 含义 |
|---|---|
| 硬约束 | 用于排除不合格结果的规则，判定为 pass / fail / unknown |
| 软偏好 | 用于排序与解释取舍的偏好，不排除候选 |
| 证据 | 本次抓取的原文片段及其元数据 |
| 主张 | 从证据提取的陈述，分事实 / 来源评价 / 系统推断 |
| 合格推荐 | 所有适用硬约束均 pass 的候选 |
| 待确认项 | 无 fail 但存在关键 unknown 的候选 |
| 排除项 | 至少一条硬约束 fail 的候选 |
| 部分完成 | 有产物但因失败或预算耗尽留下未完成检查的终态 |
| 无匹配结果 | 成功执行但无合格项的结果类型，非失败 |
